# معماری API پروژه GodOfDars

این پوشه مرجع طراحی API عمومی GodOfDars است. در این مرحله هیچ کد اجرایی،
endpoint یا وابستگی جدیدی اضافه نشده است؛ فقط مرزها، قراردادها و مسیر اجرای
backend چندکلاینتی مشخص شده‌اند.

## اسناد

- [ARCHITECTURE.md](ARCHITECTURE.md): معماری کلان، امنیت، داده، مقیاس‌پذیری،
  احراز هویت تلگرام و استقرار
- [ROUTES_V1.md](ROUTES_V1.md): فهرست کامل endpointهای نسخه اول و قواعد قرارداد
- [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md): ترتیب پیاده‌سازی، دروازه‌های
  کیفیت و معیارهای آمادگی انتشار
- [../../app/api/README.md](../../app/api/README.md): ساختار پیشنهادی ماژول‌های
  داخل `app/api`

## تصمیم‌های تثبیت‌شده

1. API بخشی از همین repository و همین backend است و در Git نگهداری می‌شود.
2. معماری نسخه اول یک modular monolith بدون state محلی است که افقی scale می‌شود.
3. بات تلگرام، API، worker و scheduler processهای جدا با service layer مشترک‌اند.
4. PostgreSQL منبع حقیقت است؛ Redis فقط برای cache، rate limit و داده موقت است.
5. ورود کاربر با Telegram OIDC، Authorization Code و PKCE انجام می‌شود.
6. هیچ Bot Token، Telegram Client Secret یا JWT signing key داخل Flet قرار نمی‌گیرد.
7. عملیات تغییر‌دهنده اقتصاد بازی بدون idempotency و تراکنش دیتابیس منتشر نمی‌شوند.
8. API عمومی از ابتدا با `/api/v1` نسخه‌بندی می‌شود.
9. خروجی‌های لیستی از cursor pagination استفاده می‌کنند، نه offset pagination.
10. شکستن سیستم به microservice تنها بر اساس اندازه‌گیری و bottleneck واقعی مجاز است.

## دامنه نسخه اول

نسخه اول API از کلاینت Flet روی Windows، Android و Linux پشتیبانی می‌کند و
قابلیت‌های پروفایل، منابع، مدرسه و دبیرها، دژ، سپر، معدن، مطالعه، سؤال روزانه،
مأموریت روزانه، نبرد، بوفه، دعوت‌ها و اعلان‌ها را پوشش می‌دهد.

قابلیت‌هایی که ذاتاً مربوط به گروه تلگرام‌اند، مانند انتشار سؤال در گروه، در
transport بات باقی می‌مانند و وارد API عمومی اپ نمی‌شوند؛ ولی همچنان از همان
service layer مشترک استفاده می‌کنند.

## مواردی که عمداً هنوز انتخاب نشده‌اند

- ارائه‌دهنده cloud و orchestration نهایی
- سرویس push notification برای Android
- ابزار دقیق APM و error tracking
- الگوریتم و کلید نهایی امضای tokenهای داخلی

این انتخاب‌ها قبل از فاز استقرار و بر اساس محیط واقعی انجام می‌شوند و مرزهای
معماری این اسناد را تغییر نمی‌دهند.
